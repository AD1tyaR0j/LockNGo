# Security & performance review — November 2026

Scope: API, admin console, customer app (web build), device simulator, dependencies.
Method: dependency audit, 40 live attack probes against running services, load tests on a
synthetic pilot-scale dataset (600 outlets, 6,000 compartments, 61,000 bookings, 2,000 users),
end-to-end flows in a real browser, and live device failure scenarios.

## Findings and fixes

| #   | Severity           | Finding                                                                                                                 | Fix                                                                                                                  |
| --- | ------------------ | ----------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| 1   | High               | `drizzle-orm` 0.44.7: SQL injection via identifiers (GHSA-gpj5-g38j-94v9)                                               | Upgraded to 0.45.4                                                                                                   |
| 2   | High               | `zod` 3.x: memory exhaustion on oversized collections (GHSA-mrhx-c7xc-m3w5)                                             | Migrated to Zod 4.6.7                                                                                                |
| 3   | High               | Zod 4 regression: outlet `PATCH {name}` reset `status` to DRAFT (unpublishing a live outlet)                            | Update schema built without defaults, `.strict()`; regression test                                                   |
| 4   | High               | Rate limits bypassable by spoofing `X-Forwarded-For` (`trust proxy` was always on); also a CPU DoS vector via scrypt    | `TRUST_PROXY_HOPS` config, default 0                                                                                 |
| 5   | Medium             | Login limited per IP only (and counted successful logins, which would lock out customers sharing one mobile-carrier IP) | Per-account limit (10 failed / 15 min); per-IP limit counts failed logins only (30 / 15 min); separate sign-up limit |
| 6   | Medium             | Locker-access limiter keyed on raw IP: IPv6 clients could rotate addresses                                              | `ipKeyGenerator` (/64 grouping)                                                                                      |
| 7   | Medium             | Admin console sent no Content-Security-Policy                                                                           | CSP, Permissions-Policy, HSTS (production)                                                                           |
| 8   | Low                | Oversized bodies returned 500 instead of 413                                                                            | Mapped to `413 PAYLOAD_TOO_LARGE`; test                                                                              |
| 9   | Low                | Expired sessions and device health snapshots never pruned                                                               | Sweeper retention (sessions +1 day, snapshots 7 days)                                                                |
| 10  | Low                | Mobile release build could talk to the API over plain HTTP                                                              | Release builds refuse non-HTTPS (loopback exempt)                                                                    |
| 11  | Low (test tooling) | Simulator's `out-of-order` scenario did not actually send a stale event                                                 | Now models genuine network reordering                                                                                |

Remaining advisories are in developer tooling only (esbuild inside drizzle-kit/tsup,
minimatch inside typescript-eslint) and do not ship to servers or users.

## Performance (20 concurrent connections, pilot-scale data)

| Endpoint                                   | Before                     | After                 |
| ------------------------------------------ | -------------------------- | --------------------- |
| Customer bookings list (50)                | 17 req/s, p50 1,113 ms     | 248 req/s, p50 78 ms  |
| Admin outlets (600)                        | 11 req/s, p50 1,615 ms     | 188 req/s, p50 104 ms |
| Admin bookings                             | 95 req/s, p50 205 ms       | 436 req/s, p50 44 ms  |
| Admin overview                             | p99 1,033 ms               | p99 201 ms            |
| Public outlets / availability / quote / me | 560–930 req/s, p99 ≤ 65 ms | unchanged             |

Causes fixed: N+1 queries (booking details, outlet simulated flag), missing indexes on
`payments.booking_id`, `device_commands.booking_id`, `storage_bookings.created_at`.
Client bundles: Zod removed from both clients via `@sl/shared/constants`
(customer booking screen chunk 18.5 KB → 2.6 KB gzip; admin JS 218 KB → 185 KB gzip).

Concurrency under load: 150 simultaneous bookings for 4 free lockers → exactly 4 succeeded,
0 overlapping bookings in a 61,000-row database.

## Before production (not fixable in code alone)

- Rate-limit counters are in memory: use a shared store (Redis) when running more than one API instance.
- Per-account login limiting lets an attacker temporarily lock a known email out of password login; revisit with OTP/CAPTCHA.
- Admin CSP needs `'unsafe-inline'` scripts; move to nonce-based CSP for stronger XSS protection.
- Admin outlet list is unpaginated (fine at 600; paginate before thousands).
- Run an external penetration test before handling real payments or physical lockers.

## Feature verification (same week)

Every user-facing feature was exercised against the running system (real browser for the apps,
the device simulator for lockers): customer app 24/24, admin website 25/25, lockers/simulator/
background jobs 11/11, security probes 40/40, automated tests 60/60.
Issues found and fixed during this pass: duplicate "Register device" buttons on the outlet page
(now a Register/Cancel toggle), and the per-IP login limit counting successful sign-ins.
Note: the customer **web preview** keeps the session in memory only, so a browser refresh signs
the user out (by design; native apps keep it in the OS keystore).
